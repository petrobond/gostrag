# Методика LLM-as-a-judge

## 1. Назначение

Внутренняя оценка качества ответов RAG и соответствия продукта требованиям ГОСТов.
Не является сертификацией и не заменяет эксперта.

## 2. Модель judge

- GigaChat 3 Ultra (128K контекста, freemium).
- temperature 0 (детерминированность).
- JSON-ответ, парсинг с извлечением массива/объекта.
- Двойной прогон при расхождении (план).

## 3. Контур A: качество ответов

| Метрика | Что оценивает | Шкала |
|---|---|---|
| faithfulness | подтверждён ли ответ контекстом | 0–1 |
| relevancy | отвечает ли на вопрос | 0–1 |
| citation | корректны ли ГОСТ и пункт | 0–1 |
| refusal | корректно ли поведение при отказе | 0–1 |
| verdict | итоговая оценка | pass / partial / fail |

Вход judge: вопрос, эталон, ответ системы, цитаты, фрагменты контекста.

## 4. Контур B: соответствие ГОСТам

1. Из корпуса извлекаются требования с модальностью «должен / следует / рекомендуется» (`scripts/extract_requirements.py`).
2. Требования категоризируются и получают severity.
3. Judge получает описание системы и артефакты (`docs/*.md`).
4. Для каждого требования возвращается статус, доказательство и уверенность.
5. Отчёт агрегирует compliance rate и распределение по severity.

## 5. Защита от искажений

- Перемешивание порядка требований в батче.
- Ограничение длины доказательства.
- Двойной прогон при confidence < 0.6.
- Калибровка на 20 примерах вручную (план).
- Фиксация модели judge в manifest.

## 6. Ограничения

- Judge может ошибаться и «подыгрывать» системе.
- Артефакты могут быть неполными.
- Оценка не учитывает юридические нюансы.
- Результат — индикатор, а не заключение.
